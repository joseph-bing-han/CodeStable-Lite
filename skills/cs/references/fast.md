# 快改：小改默认通道

本姿态继承 [Task 主线](task.md) 与 [计划后自治](autonomy.md)。简单改法询问直接回答且不创建 Task；确认要执行快改后，先分析并写入最小 `ff` 依据，再创建 Task。用户可以明确不要 `ff`，但 **Task 不可豁免**：实施前创建，完成可观察批次后更新，验证通过后归档，再回写关联文档结果与最终状态。

小需求、用户要快、或一次可做完的低风险改动时使用。不写完整 Design / 检查表 / 验收清单；**轻扫并形成结论后，先写 `ff`，再建 Task 和实施**。记录保持轻，不颠倒开发顺序。

触发示例：快速、快改、fastforward、别走流程、直接开干、小改一下（且规模配得上）；以及用户只给明确小目标、未要求常规 issue 时的**默认**出口。

**`ff` 例外：** 用户**明确**说不要业务痕迹 / 别写 issue / 别落盘 ff 时，可不写 `ff`；仍须执行完整 Task 创建、批次更新、验证、完成和归档。真相失效仍应同步 project spec 或标漂移。未明确拒绝 `ff` → 必须落 `ff`。

## 原则

**小改默认走这里，不是“可有可无的捷径”。** 两层保护：改前用最简 `ff` 明确依据；改后回写真实结果。

**入口轻，顺序不省。** Task 前创建 `NNN-o-ff-名称.md`，写清目标、改动范围、拟验证方式及规格影响；不是空壳，也不预填成功结果。同会话小改同样先 open，Task 归档后再回写并关闭，不能直接首次创建 `x-ff`。

**命中的 spec/decision 是约束，不是参考。** 违反要么先改 spec（须授权），要么别按违反方式实现。

**复杂就跳车。** 硬推快改的成本高于切回 Design / 常规 issue。

## 命名与序号

见 `SKILL.md`「命名与序号」：

- 独立快改：`codestable/issues/{NNN}-o|x-ff-{名称}.md`
- Epic 快改：`codestable/epics/{epic}/issues/{NNN}-o|x-ff-{名称}.md`
- 只在改动明确推进某个 Epic 边界时挂入该 Epic；否则留根 issues，不因代码路径碰巧相邻而挂靠
- `NNN` = 所属 issues 树（含 `done/`）已有最大序号 + 1（至少三位）
- 模板：`templates/entities/ff-issue.md`，`type: ff`（四答自检，非四节空槽）
- 每次快改只生成这一份 `NNN-o|x-ff-...md` 正本。Task 日期、Task slug 与 archived 每日序号不得进入 `issues/` 路径，也不另建日期目录、任务目录、`fix-note`、`report` 或 `analysis` 文件；需要保留的修复说明直接收进 `ff` 四答或 Task 记录。

## 行动指南

### 1. 改前（开工协议的轻量版）

对整个 `codestable/` 做路径浏览 + 关键词 grep，再按命中深读（协议见 `SKILL.md`「开工协议」）：

1. **这块以前栽过吗？** → `notes/`、递归检索根与各 Epic 的 issues（含 `-x-`、`done/` 与历史 `ff`）
2. **有没有已拍板的写法/边界？** → **project spec**（重中之重）+ 相关 epic spec

本会话同主题已扫过且无新写入可复用。没命中按自己判断写很正常。

快改不要求完整现状说明；一句话能说清触发→结果即可。说不清或跨多边界 → 跳出快改。

结论明确后，先按归属取下一编号、创建或更新 `o-ff`，必要时同步当前规格依据或标漂移，再创建或恢复关联这些文档的 Task。`ff` 仍只回答四件事：准备做什么、涉及哪些文件、怎样验证、预计对 `codestable/` 有何影响；使用“计划/待验证”区分尚未执行的内容。用户明确不要业务记录时，在 Task 记录该例外与现有依据。

### 2. 实现时守住的红线

- **先想放在哪儿**：归属仍对 → 扩展正确模块；业务形状已变 → 先抽/重切再改，别在过载 if-else 里硬塞。别往顺手文件里塞。
- **只写用户明确要的**：不提前抽象、配置开关、工厂、无关兜底。
- **只动该动的**：同文件无关丑代码不顺手改；发现记到「顺手发现」。为目标服务的最小结构步（抽取到正确归属）可以做，不是无关重构。
- **默认最少总复杂度**：不是「diff 最小、文件形状不动」；细节见 [economy](economy.md)。
- **反射信号就停**（任一条出现就评估是否跳出）：改动跨 3+ 能力边界；要引入新术语或冲突统一语言；要动 project/epic 已定模块/产品边界；范围翻倍；文件/函数已明显过载还在硬塞。停的是范围失控，不是禁止该做的抽取。
### 3. 验证

每个实施批次先更新 Task，再跑最相关检查；失败返回修改、更新 Task 与复测。入口失败时先修环境，再选择证据不降级的替代验证。验证通过后准备已有 `ff` 的结果回写，不再首次补建事项，也不等待普通效果确认。

### 4. 准备已有 `ff` 的结果回写

核对 Task 前创建的同一 `o-ff` 正本，不重新编号或另写一份。归档前准备真实结果与证据，归档后再落实最终状态。

正文只填：

- 做了什么
- 改了哪些
- 怎么验证的
- **对 `codestable/` 的影响**（必选其一：无影响 / 已同步 spec / 已知漂移 / 应升级流程）
- 顺手发现（可选）

写得轻：总共十几行通常够。不要迷你 Design。

执行 [自动回写与沉淀](retention.md)：有规格增量或真相失效且确定 → 按归属同步 Project / Epic Spec 的具体小节，并记录结论、路径与证据；跨事项坑点自动查重写 Note，稳定重复流程检查 Tool。无增量写明依据。

不确定 → 在受影响规格章节及 ff 标漂移，记录缺什么证据、关联事项与复查触发（下次命中该主题或关闭时）。下一次相关开工先复查，证据齐备即修正并清除漂移标记，不能只归档 Task 让漂移失联。若漂移阻碍本次正确性或验收，必须先解决或 blocked，不能以“已知漂移”宣布完成。

### 5. 收尾

完成验证并准备沉淀后，更新 Task、标记 completed 并原子归档，运行 cleanup / scan。随后回写同一 `ff` 的实际结果，按归属同步相关 Spec 等文档，最后将 `status` 改为 `closed`、路径从 `-o-` 改为 `-x-`；更新引用并回读确认。归档前在 Task 记录预期改名映射，归档后在 `ff` 记录原路径与 Task archive；不修改冻结 Task。回写失败不能宣布完成，按 task.md 恢复同一出口。

最终汇报告知 `ff` 路径（无 `ff` 时说明原因）和 Task archive；默认不 commit。只有已经授权 commit 时，才 scoped 提交本次代码、`ff` 与 spec 同步。

## 什么时候自动升级快改

任一情况出现时，保持同一 Task，自动切 Design 或常规 issue 后继续：

- 改动涉及 3 个以上子系统/能力边界
- 需要引入新术语或与统一语言冲突
- 要改 project / epic 已定边界
- 用户追加需求使范围翻倍
- 需要多轮验收或正式质量承诺清单

先将既有 `ff` 原位升级为常规 Issue，保留本树编号与执行证据，去掉文件名中的 `ff-` 并更新引用；补齐方案后更新同一 Task，再继续实施。已写代码如实标「已部分实现」，不重建一个事后 Issue 冒充前置依据。用户明确禁止业务文档时仍守住授权边界。

## 不做什么

- 不写 Design / 九项清单 / 完整验收表
- 不创建没有目标、范围或验证依据的空壳 `ff`，也不做完后才首次补建
- 不把 `ff` 写成迷你 Design 或常规 feature issue
- 不在 `ff` 之外复制一份修复说明，也不模仿历史日期目录或旧 `fix-note` 结构
- 不因「要快」跳过 `codestable/` 轻检索与验证
- 不在用户未明确拒绝痕迹时省略 `ff`
- 不自动 push / 部署

## 收尾汇报

做了什么、怎么验的、`ff` 路径（或无痕迹例外）、对 `codestable/` 的影响和 commit 状态。未授权 commit 时保持未提交，不为可选提交打断工作。顺手发现单独列出。

## 应用场景

小功能、小修复、布局微调、用户明确不要完整流程、以及默认的小而明确改动。

不适用：模糊需求 → Talk；明确要设计 → Design；bug 走 Complain（定位后先准备 `ff` 或常规 Issue，再进 Task 试修；用户明确不要痕迹除外）；大边界变化 → Epic / 常规 issue。
