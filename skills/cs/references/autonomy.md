# Autonomy：计划确定后的无人值守执行

本文件定义 `cs` 从“Question 直接回答或继续澄清”切换到“Issue 创建 Task 并持续执行”的边界。它与 [Task 主线](task.md) 配套：只有已判定为 Issue，且 Task 中的目标与步骤一旦足以开工，才构成计划承诺；后续分叉由 Agent 自主收敛，不把机械推进重新交还用户。

## 1. 两个阶段

### 计划确定前

简单 Question 直接回答，不创建 Task。若无法可靠判断是 Question 还是 Issue，必须在 Task 创建前使用 AskQuestion；目标、范围、验收或不可逆授权尚不足时，也可以使用 AskQuestion。每次只问真正会改变“是否创建 Task”或后续计划的问题；把推荐项放在首位并说明关键取舍。此阶段属于 intake，不做 substantive work，不创建空壳 Task。

一旦满足以下条件，就结束澄清：

- 能一句话描述完成后的可观察结果；
- 已确认本次是 Issue，而不是可以直接结束的 Question；
- 能列出最小充分范围和不做什么；
- 能列出执行步骤与验证入口；
- 已识别需要的人类不可逆授权，例如 push、部署、删除关键数据；没有授权的动作排除在计划外。

### 计划确定后

把目标、步骤、验证和排除项写入 active Task，即进入无人值守阶段。此后：

- **不询问普通推进，只询问必要澄清与授权**：可从上下文推断的低风险细节直接决定；缺失信息会实质改变目标、正确性或权限且无法查证时，使用 AskQuestion。不得把“是否继续”作为问题。
- 自动选择推荐方向，更新 Task 后继续当前 run。
- 计划内步骤、Task create/update、测试、Review、修复、复测、文档同步、complete、archive 与 cleanup 都是机械继续。
- 不因一个批次完成、一个测试首次失败、发现小偏差或产出中间文档而停下。
- 持续执行直到目标、计划内步骤、必要 gate、Task 归档全部完成。

规则按宿主指令层级执行；用户最新明确要求优先于 Skill 默认建议，但不覆盖更高优先级的系统、开发者和安全边界。若规则造成阻塞，指出具体文件、原句和适用原因，区分明文要求与自己的推断，不笼统归因于“流程规定”。

## 2. 自动择优顺序

出现多个可行方向时，先排除违反用户目标、项目 Spec、既有公共契约、安全边界或数据完整性的方案，再按以下顺序选择：

1. **正确性与契约一致性**：能完整满足目标并保持 Project Spec、Epic、Issue、代码和测试一致。
2. **风险**：优先降低数据、安全、并发、兼容、发布和不可恢复失败风险。
3. **可逆性**：优先容易验证、容易回退且不会锁死后续选择的方向。
4. **证据强度**：优先能用现有测试、真实接口、最小穿刺或可观察行为证明的方向。
5. **总成本**：在同等正确下，选择实现、运行、维护和上下文成本更低的最小充分变化，而不是机械追求最小 diff。
6. **局部性**：仍相同时，选择影响边界更窄、复用现有责任归属的方向。

把选择、理由和受影响步骤写回 Task；不把多方案清单抛给用户。

## 3. 偏差与失败循环

### 实现或文档偏差

- 不改变目标与公共契约：更新计划/Task，直接继续。
- 原方案不成立但目标仍明确：回到设计，按自动择优顺序重选方案，再实现和验证。
- 快改膨胀为多批工作：自动升级为受管理强度，在同一 Task 中补步骤和相关 Issue / Epic；Task 主线不重建、不暂停等待同意。
- 发现范围外问题：只在它是完成原目标的必要前置时纳入；否则写入 Task 的“顺手发现”或现有事项候选，不扩展本次完成条件。

### 测试、Review 或工具失败

```text
收集证据
  -> 定位失败属于实现、测试、环境还是契约
  -> 选择最小安全修复或替代验证
  -> 更新 Task
  -> 实施
  -> 重跑相关验证
  -> 有新证据表明影响更广时扩大回归范围
  -> 仍失败则用新证据重复
```

- 测试失败不是 checkpoint；修复根因后继续。
- Reviewer 不可用时，自动重试一次；仍不可用则选择宿主可用的独立只读子 Agent。不得用实现者自评冒充独立 Review。
- 命令、依赖或网络入口失败时，先诊断环境，再选择等价且证据不降级的本地入口；不能伪造通过。
- 单写者流程中发现 Task hash 已变化时，重新读取正本、合并外部修改并用新 hash 重试；active / archived 内容分叉时保留双方证据并 fail closed。

验证以用户要求、项目必跑检查和实际风险为准。先跑覆盖受影响行为的聚焦检查；通过后仅因新改动、失败或未解决风险才重跑或扩大。不要为文案小改跑整套业务回归，也不要添加只复述实现的测试。独立 Review 在用户要求、项目规定或变更风险值得时使用，不为每次小改强制委派。

## 4. 用户中途纠正与宿主能力

新消息到达时，先停止受影响的旧方向，确认在途命令和子代理状态，再继续写入；用户中途纠正优先于旧计划，不要因旧 Task 已承诺而忽略最新要求。无关、仍获授权的工作可继续。已执行副作用不会因 steering 自动撤销，撤销也须核对权限。

- 目标不变、补充细节或追加必要步骤：保留既有步骤标题与顺序，更新记录或追加步骤，在同一 Task 继续。
- 用户替换目标，或必须删除、重命名、重排承诺步骤：在旧 Task 记录新目标、替代 slug、已完成证据和剩余范围；用 `set-status cancelled -> archive` 结束旧 Task，再创建关联旧归档的新 Task。旧 Task 若 blocked，先显式恢复 active 并记录原因，再取消。不得把放弃的步骤标 done，不放宽 runtime 的计划保护。
- 取消到新建之间中断：恢复时读取旧归档的替代 slug，先 scan，恢复已存在的新 Task 或按记录创建；不复活旧 Task、不重复新建。取消归档沿用 runtime 的现有恢复机制。

首次需要并行、原生 Todo、等待或中途引导时，核对宿主实际暴露的工具与 schema，见 [宿主适配](runtime-adaptation.md)。互不依赖的调查、文档核对和独立只读 Review 值得并行时主动委派，给清范围、输入、输出和禁止写入边界。父代理是 Task 与共享业务文档的唯一写入者；后台启动不等于交付，必须收回结果并检查失效输出。没有相应工具就串行，不虚构异步执行、推理档位切换或独立 Review。

## 5. 授权边界如何自动处理

无人值守不扩大用户尚未授予的权限。commit、push、创建 PR、部署、生产写入、关键数据修改、删除历史、付费外部操作与 Epic 关闭按各自契约取得明确授权；帖子中的主动性示例不是授权来源。先完成已授权且可逆的准备，使待批准动作具体、可审查；必要时在动作前使用 AskQuestion，不要求授权一定发生在 Task 创建前。

如果用户一开始已经明确授权上述动作，则把授权写入 Task，计划后按既定安全 gate 自动执行，不重复询问。

未授权动作若本就在用户目标外，保持排除，不为可选发布或提交打断工作；若是达成目标的必要条件，不得自行删掉该完成条件。凭证、登录或外部人工交互缺失时，先寻找等价证据；没有替代则把 Task 标 blocked，记录已完成准备、精确阻塞、所需输入和恢复动作，向用户请求必要介入。不声称完成、不归档、不反复尝试同一失败入口。

## 6. 停止条件

只有同时满足以下条件，才允许停止并给出完成式答复：

- 用户目标和 Task 完成条件全部满足；
- 计划内没有 pending / in-progress 步骤；
- 测试、Review、QA、Agent 可执行且可观察判定的验收、文档同步等必要 gate 已通过；不临时添加无依据的人类 checkpoint，但用户中途新增的明确验收与真正必要的授权必须纳入；
- 没有 blocking finding 或未解决冲突；
- Task 已从 `completed` 原子归档为 `archived`；
- cleanup 和 scan 证明 active 同名文件不存在。

否则继续获授权的工作；真正阻塞时按上节保留恢复点。不要把普通“下一步建议”或中间总结当作终点，也不要为了无人值守越权或伪造完成。
