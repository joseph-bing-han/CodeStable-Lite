# 自动回写与沉淀

本规则连接前置业务依据与最终回写，不是新的 Skill 或第二套 Task。分析讨论后先准备相关文档，再创建 Task；实现验证后准备回写内容，Task 归档后更新所有关联文档的结果与最终状态。命中才读取对应细则，不要求用户点名 Spec、Talk、Note 或 Tool。

## 先判断是否应该写

仅 Question、只读 Review、用户明确只要对话或禁止业务文档时，不因本规则新建业务产物。对已获授权的实现与文档工作，必要前置依据与回写属于工作的一部分；只创建本次必要目录，不调用完整初始化，不补空壳 Vision/Epic。只有 `tasks/` 不代表已授权完整制度记忆，但也不能据此跳过默认应有的 Issue / `ff` 前置依据；用户明确禁止时记录例外。用户禁止写规格时，报告与现有规格的具体漂移，不暗中写入。

证据不足、实现未落地、仍属未来或候选的内容不能伪装成当前真相。已有同主题产物优先更新，不复制第二份；已经回写且没有新事实时不重复沉淀。

## 1. 开始执行前：先有业务依据

分析讨论形成结论后，先创建或更新相关 Issue、`ff`、Epic Spec 或已有目标文档，再创建或恢复 Task。记录目标、范围、已确认方案、验证方式和受影响规格；不能完成 Task 后才首次补建这些依据。Project Spec 此时只核对当前事实、补必要入口或标明漂移，未实现目标仍在 Issue / Epic。讨论结论需保存时同时按下文捕获 Talk。

## 2. 验证通过：准备事实与回写位置

先根据 Issue 的物理路径确定归属，再核对验证结果和受影响的现有规格。归档前准备以下内容与证据，归档后落实结果和最终状态；多批推进中可同步已验证事实，但不能因此省略最终回读：

- **独立 Issue / 无业务 Issue 的独立实现**：已实现、已验证且当前成立的能力、行为、责任、约束与取舍，自动维护 Project Spec；不必等 Issue 关闭。仅测试或内部整理且没有长期事实变化时，记录“无规格增量”及依据，不制造章节。
- **Epic 内 Issue / 直接切片**：自动维护所属 Epic Spec 的当前理解、推进状态、剩余阻碍和毕业候选；区分已验证事实与目标方案。未关闭 Epic 的成果不得提前毕业到 Project Spec。
- **ff**：同样先判断归属。仅修复偏离原有规格的实现时可无规格增量；确有新事实或旧真相失效就同步对应 Project / Epic Spec，不能只勾“已同步”而不写内容。
- **已有 Project Spec 被未毕业 Epic 的工作直接证伪**：在原章节标明具体漂移、适用范围和 Epic 入口，不把未来方案写成主线事实。

按 [spec](spec.md) 组织内容。必要的规格入口应在前置阶段准备，只覆盖已核对事实与具体漂移，不生成完整项目概述或猜测未调查区域。执行中才发现的新事实补入同一正本，不能以“最后会沉淀”替代原本已知的前置依据。用当前能力的具体说明替换过时正文；历史链接仅作证据。

## 3. Task 归档后：更新所有关联文档

确认 `complete -> archive -> cleanup / scan` 成功后，再逐一更新相关 Issue / `ff`、Project / Epic Spec，以及实际受影响的 Talk / Note / Tool / Vision 索引。写入实际结果、验证依据、最终推进状态和 Task archive；不只改日期或勾“已同步”。无变化的关联文档核对后不强行改写，留下不适用或无增量依据即可。

普通 Issue 未获关闭授权时保留 `status: open`，正文明确本轮已完成及关闭就绪情况；`ff` 回写后按默认规则改 `closed` 与 `-x-`；Epic 关闭仍须授权。Project Spec 没有统一 open/closed 状态，更新的是当前事实与漂移判断，不能自造状态字段。

回读目标章节和实际路径，确认引用可达、状态一致、过时表述已替换。Task 归档不替代该出口；只剩回写时不创建第二个 Task。回写中断按 [Task 恢复](task.md) 从归档证据与业务正本继续，不修改冻结 archive。未回写完成不得给出完成式答复。

## 4. 关闭：复核毕业与授权

关闭执行 [close](close.md)。独立 Issue → Project Spec；Epic Issue → Epic Spec；Epic 经用户确认关闭 → Project Spec，并检查 Vision。关闭 Task 归档前核对证据、授权和毕业内容；归档后先完成内容级回写，再改业务 closed 与路径状态。此前已同步的结论复核即可，不重复搬运。

实现完成不自动关闭常规 Issue。用户已授权收尾时直接执行；未授权时保留 open，并在事项中留下关闭就绪情况和实际回写位置，不阻碍实现 Task 完成。若 Epic 已满足关闭条件，主动呈现具体毕业候选并用 AskQuestion 请求一次关闭授权，不等待用户记起“关闭 Epic”。用户要求仅实现、不询问或暂不关闭时，只记录待授权候选，不再询问。拒绝关闭不妨碍实现 Task 归档；若本次目标本来就是关闭而缺必要批准，则 Task blocked，不把关闭目标偷换为实现完成。

关闭记录必须是“结论 → 目标文件及章节 → 验证依据”；无规格增量时写明原因。仅留链接、空候选或把执行日志整体复制到 Spec 不算回写完成。Epic 的毕业内容应让只读 Project Spec 的人理解当前能力；最后才改 closed 与路径状态。

## 5. 讨论收束：自动捕获 Talk

多轮讨论发生过有价值的纠正、取舍或开放问题，且用户已认可方向并要求推进，或者明确要求整理/暂存时，自动按 [talk](talk.md) 写入或更新同主题 Talk，再进入已授权的出口；无需额外询问“要不要写 talk”。Talk 保留如何想清楚和实际出口链接，不是规格真相。简单问答、一句明确小改、未收束的随口想法不落 Talk。仅同意整理不等于授权实现，未确认分歧仍标开放。

## 6. 验证之后：自动提炼 Note

当修复、调查、用户纠正或流程学习得出会改变下一次判断的非显然知识，并有证据与适用条件时，自动按 [note](note.md) 查重并更新 Note；不等业务事项关闭。记录结论、触发场景、证据、失效边界与来源。普通测试通过、代码已直说的行为、一次性进度和尚未验证的猜测不生成 Note；启动规则也不自动扩写。

## 7. 重复流程：有证据才生成 Tool

发现已经跑通且有实际重复需求、步骤稳定、输入输出明确、适合自动化的流程时，自动按 [maketools](maketools.md) 检索并复用现有工具；确有缺口才在本次授权范围内新增或更新 `codestable/tools/` 的可执行工具与说明。不是只写一篇“以后可自动化”的文档。

生成前确认重复使用证据与收益；生成后用安全样例复跑，验证输出和失败分支。仅一次探索、仍需人判断的流程、超出当前范围的大型自动化，只在已有 Note 或 Task 留候选。工具生成不授权危险执行：删、覆盖、生产、发布、权限等必须有显式操作边界；不得绕过人工节点，不把凭证写进工具或文档。验证不了就不能标“稳定工具”。

## 完成检查

归档前在现有 Issue / `ff` 或 Task 批次记录中写清回写准备与依据；归档后在业务正本中给出规格、Talk、Note、Tool 的**已更新位置 / 无增量原因 / 待授权或未验证原因**，不可预先把待回写标为已完成。不新增平行报告或四项空模板；未命中的类别可合并说明。Task 的 related_docs 索引启动时的实际正本，关闭改名的映射归档前记录，最终链接在仍可变的业务文档中维护。

该检查由 Agent 执行，Markdown runtime 只验证 Task schema、步骤和状态，不会自动理解业务结论，也不保证模型每次都触发。用真实行为场景检查规则是否被执行，不能把关键词单测通过当成真实模型成功率。
