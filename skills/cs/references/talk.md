# Talk：讨论与初步规划

洞察真实诉求（用户开口常是方案或表面诉求），收束成可判断的初步安排。聊完后用户认知应更清楚；出口是快改、独立 issue、Explore issue、epic、Vision，或继续澄清。

姿态与管理强度见 `SKILL.md`。质量候选规则见 [quality](quality.md)；UI 草图见 [ui-spec](ui-spec.md)。

## 原则

先看清是什么，再让用户看见他看不见的，最后收住边界、终点与出口。

**先讨论，再落盘。** 不边聊边维护整理稿。阶段性复述让用户纠正；仅当用户明确说“差不多了 / 整理一下 / 落盘 / 写个 talk”后写入 `codestable/talks/`。

**Talk 正文优先按讨论顺序。** 落盘时按议题当时如何提出、纠正、收束来写，让后来者能顺着对话理解「怎么想清楚的」。模板与清单只保证**该留下的信息别丢**，**不**规定必须先「真问题」再「术语」再「决策」的固定章节骨架。同一结论若讨论中被推翻，写在纠正发生的位置，并标明最终以何为准；不要为了套模板把整场讨论打乱重排。

**能查先查，不明白再问。** 不把猜测当需求或事实。偏好可商量，约束不能绕过；稳定约束最终进 project / epic spec。

**做第二层推演。** 主动想影响谁、改什么工作流、牵动哪些历史约束、长期代价。风险按场景选，不机械全列。

**具体变化做质量扫描。** 用九特征找会改变方案/验收/长期代价的候选；不逐项问“是否需要”。候选项在 Talk 中尚非承诺。

**UI 分歧优先画出来。** 讨论草图标“目标”或“示意”；确认前不是 spec。

**一次一个分叉。** 每个问题给推荐答案与理由。

**初步规划是收束的一部分。** 出口草案须含目标、范围、验证、依赖、暂不纳入与理由。管理是否值得见 `SKILL.md`「管理强度」。

**只记录确认过的边界。** “不做什么”须用户说过或同意你提出的排除项。

## 行动指南

复用已掌握上下文；项目有 `codestable/` 时先跑 `SKILL.md` 开工协议（主题检索）。想法来自 Vision 或落在已有 epic 时深读对应分支。

提问只问缺口：已从仓库确认什么、还缺什么、当前最关键分叉。按“事实 → 推荐 → 请用户决策”。

至少一轮影响扫描（兼容、数据、命名、外部依赖、发布/回滚、维护成本等）；涉及质量时用 [quality](quality.md)。候选质量目标写成草案（条件、结果、来源、证明方式），仍标为候选。

用户未确认停止前：不写 talks，不更新 Vision，不建 issue/epic。

收住条件：真问题一句话且用户确认；做什么有轮廓、已确认/未确认边界清楚；最大未知已标出。最多三到五轮深挖；争的是事实且半小时内能验证时，动手查比继续聊更省。

收住后给出口草案；用户确认安排后再落盘并执行对应出口。

**落盘写法：** 以讨论节拍为骨架（每节 = 一轮推进或一次关键纠正）；节内写清当时谈了什么、查到什么、用户定了什么。清单中的项嵌在对应节里即可，不必再开一套平行目录。极短 talk 可以只有几段连续叙述，仍须覆盖清单中实际出现过的项。

## 产物契约

确认前无文件。确认后：`codestable/talks/{NNN}-{名称}.md`（扁平，无日期目录；`NNN` = 该目录已有最大序号 + 1，至少三位）。

**必须留下的信息（有则写、无则省略；顺序跟随讨论，不强制下列标题）：**

- 开场意图 / 原始说法（用户怎么起头的）
- 过程中的关键纠正与最终以何为准
- 已确认决策与稳定约束
- 术语（在首次需要处定义即可，可集中也可随文）
- 影响、风险与取舍（谈及处写）
- 候选质量目标（谈及或扫描到时；非承诺）
- UI 草图（若有）
- 仍开放的分歧 / 最大未知
- 出口：已执行或建议的下一步、暂不纳入

**禁止：** 为套模板把讨论顺序打乱；用空章节凑「模板完整」；把未确认内容写成已确认。

用户只确认整理 talk → 只写 talk。同时确认安排时再执行出口：

- **快改**（小改默认）→ [fast](fast.md)（完成后在所属 issues 树写 `NNN-x-ff-名称.md`；用户明确不要痕迹时可无 ff）
- 目标全景 → Vision
- 独立 feature/bug/chore/refactor → `codestable/issues/{NNN}-o-{名称}.md` + `templates/entities/issue.md`（设 `type`）
- 已有 Epic 的 feature/bug/chore/refactor → `codestable/epics/{epic}/issues/{NNN}-o-{名称}.md` + `templates/entities/issue.md`
- 新 epic → `codestable/epics/{NNN}-o-{名称}/spec.md`；首个所属 Issue 创建时再建同目录 `issues/`
- Explore issue → [explore](explore.md)（按归属写入根或 Epic 的 issues 树）
- bug → [complain](complain.md)
- 已有 epic 规格变化 → 谈记录决策后 [spec](spec.md)

## 收尾汇报

确认前：聊清了什么、仍不确定什么、质量风险候选、建议出口。落盘后：顺着讨论主线一两句说清定了什么，再列写入文件。路径不作主要成果。

## 应用场景

局部想法未清、方向摇摆、交代不完整、想先聊再动手。

不适用：维护 Vision/当前真相/epic 活规格；写实现设计；已明确 bug；写代码。全景构想 → Vision；上游规格大体稳定只差落到开发者可读规格 → Spec。
