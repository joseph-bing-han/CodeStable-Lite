# 修正业务文档与 Task 的开发顺序

## 问题与证据

用户指出，GPT-6 适配工作先创建并完成 Task，之后才补 Issue/Spec，颠倒了需求依据与执行账本的关系。

- 历史记录：`codestable/tasks/archived/2026-09-12-001-adapt-cs-lite-gpt6.md`，保留原始时序，不倒填或复活。
- 当前 `task.md` 要求先创建 Task，再读取仓库、分析、设计和写文档。
- 当前快改规则要求代码与验证完成后才创建 `ff`。
- 当前完成条件将 Task 归档视为最后一道出口，缺少归档后关联文档状态回写。

## 已确认的修正结论

开发顺序统一为：

1. 用户提出问题或需求。
2. 分析、讨论并形成目标、范围、方案和验证结论。
3. 创建或更新本次相关 Issue、Spec 等业务文档。
4. 创建或恢复 Task，并关联已存在的业务依据。
5. 实施修改，按可观察批次更新 Task。
6. 测试；失败返回修改与更新 Task，直到验证通过。
7. 完成并归档 Task。
8. 更新所有相关 Issue、Spec 等文档的结果、最终状态与链接。
9. 核对无遗漏后结束。

前置文档不是事后报告；Task 归档也不代表整个工作流已经结束。

## 范围与边界

- 同步技能入口、Task/自治/回写契约、相关姿态、模板、宿主提示和中英文 README。
- 增加能阻止旧顺序回归的契约检查，并验证已有 Task runtime 不被破坏。
- 快改仍保持四节短 `ff`，但先记录明确目标、范围与验证方式，归档后补结果和最终状态。
- 简单 Question 不创建 Task；用户明确禁止业务文档时服从授权，不把该例外扩展成默认 Task-first。
- 按需复用或创建相关文档，不为一次修改强制生成整套 Vision/Epic。Project Spec 前置阶段只记录当前事实和具体漂移，未实现的目标保留在本 Issue 或 Epic。
- Task 正本仍单写者、SHA-256 保护、原子归档；不修改已归档历史，不改变 Task schema。
- 文档最终状态必须与证据和授权一致；未获关闭授权的常规 Issue 保持 open 并注明完成/关闭就绪，不把 Task 归档当成关闭授权。
- 明确已授权“关闭并提交”时的出口顺序：Task 记录提交准备与验证，实际提交在归档及业务回写之后，不把未执行提交提前标为完成。本次只修正规则，不执行提交。
- 不提交、不推送、不部署，也不修改仓库外已安装技能副本。

## 验证安排

- 定向检查前置文档早于 Task、测试失败回到实施、归档早于最终业务状态回写。
- 检查快改、受管理实现、讨论转行动及归档后中断恢复没有相反指令。
- 运行现有标准库测试、仓库契约检查、差异格式检查与 Task scan。
- 独立只读复核跨文件一致性；关键词检查不能冒充真实模型行为成功率。
